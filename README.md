# TG 签到控制台

一个用 Docker 部署的 Telegram 工具集，包含两个互相独立的模块：

1. **群组自动签到**：按设定的 cron 时间向指定群组发送签到指令，Web 面板管理群组、查看日志。默认由**机器人**执行（只需 BotFather 的 `bot_token`，不需要 `api_id`）；也可以切换成用你自己的账号执行（需要 `api_id` / `api_hash`，MTProto）。**支持多个 Telegram 账号和多个机器人**，每个群组可以单独指定用哪一个。
2. **AI 聊天机器人**：接入任意兼容 OpenAI 接口的大模型，在私聊或群里 @ 它时自动回复；开启 Telegram Business 后还能以你本人身份回复私聊（秘书模式）。同样只需要 `bot_token`，支持同时挂多个机器人。

两个模块可以只用其中一个，都只依赖 bot_token 时可以零 api_id 跑起来。

另外内置了**每日补签**（定时点没在线就在上线后补一次）和**备份 / 恢复 / WebDAV 云备份 / GitHub 同步**，专门应对免费 PaaS「会休眠、没有持久卷」的问题。

## 功能

**签到**
- 两种执行者：机器人（Bot API，默认）或自己的账号（MTProto，备用），**每个群组可单独指定**
- 支持多个群组，每个群组可单独设置签到指令和多个执行时间
- **多账号**：每个账号独立保存 api_id/api_hash/手机号/代理与登录会话，互不影响
- **多机器人**：每个机器人各自一条轮询线程、各自的群列表，互不干扰
- Telegram 账号登录（扫码或验证码 + 两步验证），会话持久化，容器重启不用重新登录
- **每日补签**：定时点没在线（容器休眠/重启）时，上线后立刻补一次，保证每天至少签到成功一次
- 中文 Web 面板：概览、群组管理、AI 机器人、账号登录、系统设置、运行日志
- 失败自动重试、随机延迟、失败关键词识别
- 发送到指定会话的运行结果通知
- 模拟运行模式，先验证连接不真发消息
- 面板密码保护，SQLite 存储所有配置与日志

**AI 机器人**
- **多智能体**：每个智能体有自己的名字、模型、接口地址、Key、人设与参数，可以同时接 DeepSeek、Kimi、硅基流动等不同服务
- 每个机器人可以单独指定用哪个智能体，没指定就跟随「默认智能体」
- 任意兼容 OpenAI `/chat/completions` 的服务：DeepSeek、硅基流动、Kimi、通义、one-api 中转等
- 三种触发方式：私聊 + 群内被 @、群内所有消息、只回私聊
- 按会话保存上下文，可配置保留轮数；上下文落库，重启后仍能接上
- 最短回复间隔限流，避免刷屏和触发 Telegram 限流
- 面板内可逐个测试智能体连通性、查看和清空对话记录

**备份与恢复**
- 一键下载完整备份（群组 + 账号 + 机器人 + 全部设置 + 登录会话），单个 JSON
- 从文件恢复，可选「替换」或「合并」；账号/机器人自增 ID 会自动重映射，群组绑定不会指错人
- **WebDAV 云备份**：坚果云、Nextcloud、群晖、InfiniCLOUD 等，支持自定义备份文件夹（保存时自动创建，多级也行）、自动上传与份数裁剪
- **GitHub 同步**：每次备份作为一次 commit 推到仓库，天然带版本历史；仓库地址可直接粘浏览器链接，404 时会反查 Token 能访问哪些仓库并给出正确写法
- **启动时自动恢复**：容器重建后本地为空时，自动从云端拉最新备份接回来

## 一、准备 Telegram API 凭据（仅「用自己的账号签到」需要）

> 默认的签到方式是**机器人**，只需要 bot_token，**直接跳过这一节**，去第六节创建一个机器人即可。
> 只有当你把「系统设置 → 谁来签到」切换成「自己的账号」时才需要下面这套凭据。

1. 打开 <https://my.telegram.org/apps> 并用你的 Telegram 账号登录。
2. 创建一个应用（API development tools），记下 **App api_id** 和 **App api_hash**。
3. 面板里填写手机号时要带国家区号，例如 `+8613800138000`。

> 这一步拿的是你自己账号的 API 凭据，不是 BotFather 的 bot token。
> 少数群里的签到机器人只认真人账号、会忽略机器人发的消息——这种群才需要切到账号模式；大部分群用机器人签到就够了。

### 申请不到 api_id 怎么办

这里有几个常见误解，先理清能省很多时间：

- **`api_id` 是「应用」凭据，不是「账号」凭据。** 它标识的是你写的程序，跟用哪个手机号登录没有绑定关系。所以可以让别的 Telegram 账号去申请，拿到后填进面板，仍然用你自己的手机号登录。这是 Telegram 文档认可的正常用法。
- **一个手机号只能有一个 api_id。** 很多人「创建不起」其实是之前已经建过了。直接打开 <https://my.telegram.org/apps>，如果页面直接显示了 api_id 和 api_hash，说明你已有，不用再点 Create new application。
- **报错多半是环境问题而不是表单问题。** 按顺序试：关掉 VPN 和代理（这是第一大原因，Telegram 对数据中心 IP 很敏感）→ 用无痕窗口并禁用广告拦截扩展 → 换浏览器 → 换网络（Wi-Fi 换手机流量）→ 等几分钟再提交一次。**不要连着狂点提交**，重复请求会触发限流，让临时封禁变得更久。
- **表单值别乱填。** App title 用普通英文名，Short name 只用字母和数字，不要用 "test"、"telegram"、全符号或纯 emoji。
- **不要用公开的示例 api_id。** 开源客户端里那份（如 `2040`）是受限示例凭据，拿来跑正式程序会收到 `API_ID_PUBLISHED_FLOOD`，还可能连带影响账号。别抄。
- **账号本身受限也会导致申请失败。** 新号、刚换号、有发消息限制的号都可能被拒。可以在 Telegram 里找 `@SpamBot` 确认账号状态。

如果以上都试过仍失败，那是 Telegram 侧对号码的限制，只能换个号申请，或者走另一条路——用 AI 机器人（不需要 api_id）。

## 二、Docker 部署

```bash
cd tg-checkin
cp .env.example .env
# 修改 .env 里的 PANEL_PASSWORD（强烈建议）
docker compose up -d --build
```

打开 <http://服务器IP:8000> ，输入面板密码进入控制台。

`.env` 中的 `PANEL_PASSWORD` 只在数据库首次初始化时生效，后续请在面板「系统设置」里修改。

常用命令：

```bash
docker compose logs -f          # 查看运行日志
docker compose restart          # 重启
docker compose down             # 停止（数据保留在 ./data）
docker compose up -d --build    # 修改代码后重新构建
```

## 三、环境变量

所有配置都可以在面板里改，下列环境变量用于首次启动或容器编排：

| 变量 | 说明 | 默认值 |
| --- | --- | --- |
| `PANEL_PASSWORD` | 面板初始密码，仅在数据库首次初始化时生效 | `admin123` |
| `DATA_DIR` | SQLite 数据目录 | `/app/data` |
| `TZ` | 容器时区 | `UTC` |
| `TGCK_CONFIG` | 启动时导入的配置 JSON（含登录会话、多账号、多机器人），仅在空库时生效 | 空 |
| `CHECKIN_MODE` | 首次初始化的签到方式：`bot` 或 `user` | `bot` |
| `PUBLIC_URL` | 面板公网地址，用于保活自检；留空则自动探测 | 空 |
| `STANDBY` | 设为 `1` 进入值守模式：只开面板，不启动调度、机器人轮询和自动备份。同一套配置部署了多个实例（主用 + 备用）时，备用实例必须打开，否则两边会抢同一个 bot 的 `getUpdates` 并重复签到 | 空 |
| `LOG_LEVEL` | 日志级别 | `INFO` |

## 四、保活（防止实例休眠）

有些托管平台的免费实例在长时间没有入站流量时会停止运行，停止期间调度器不运行，自动签到会漏掉。要解决这个问题必须区分两层，**只做第一层是不够的**。

### 第一层：容器内自检（本程序内置）

一个后台线程按设定间隔请求自身的公网 `/health` 地址。在「系统设置」里可以配置：

- **保活自检**：开关，默认关闭；设置了 `PUBLIC_URL` 时默认开启。
- **保活间隔**：默认 300 秒，最小 60 秒，最大 3600 秒。
- **保活目标地址**：留空时自动探测——用公网域名访问一次面板，程序会记住该地址。也可以通过 `PUBLIC_URL` 指定。
- **立即自检**：手动触发一次，验证地址是否可达。

面板会显示最近一次自检的时间和结果。连续失败时「运行日志」里会出现「保活自检」记录，可用来排查地址是否写错、域名是否可达。

> 限制：请求必须打到公网域名，访问 `127.0.0.1` 不经过平台入口，不算入站流量。
>
> **更关键的限制**：实例被平台停机后，这个线程会一起消失，它无法唤醒已经睡下去的自己。所以这一层只能延长活跃窗口、提前暴露可达性问题，**不能真正防止休眠**。

### 第二层：外部定时唤醒（必须配置）

真正防止休眠要靠外部定时器，由平台之外的机器发起请求。仓库自带 `.github/workflows/keepalive.yml`，用 GitHub 的服务器每 10 分钟请求一次面板：

1. 在仓库 `Settings → Secrets and variables → Actions` 添加：

   | Secret 名称 | 值 | 说明 |
   |---|---|---|
   | `PANEL_URL` | `https://你的面板地址` | 必填，程序会自动请求该地址的 `/health` |
   | `PANEL_TOKEN` | 你的面板密码 | 可选，配置后会额外验证登录态 |

2. 到 `Actions → keepalive → Run workflow` 手动跑一次，确认输出里是 `HTTP 200`。
3. 之后它会按 cron 自动执行。GitHub 的定时任务在高峰期可能延迟几分钟，所以间隔取 10 分钟，留足余量。

> **实测提醒（重要）**：GitHub Actions 的 `schedule` 属于「尽力而为」的调度，不是精确定时器。实测中新建工作流的首次定时触发可能延迟 30 分钟以上甚至更久，且高峰期可能直接丢弃排队任务。它适合做「兜底」，不适合作为唯一手段。
>
> 另外，仓库连续 60 天无提交后，GitHub 会自动暂停定时任务，需要回来手动点一次启用。

**建议再加一个专门的定时服务做冗余**（更可靠，配置一次就不用管）：

| 服务 | 免费额度 | 配置方式 |
|---|---|---|
| [UptimeRobot](https://uptimerobot.com) | 50 个监控 / 5 分钟间隔 | 新建 HTTP(s) 监控，URL 填 `https://你的面板地址/health`，关键词填 `ok` |
| [cron-job.org](https://cron-job.org) | 不限数量 / 1 分钟间隔 | 新建 Cronjob，URL 同上，开启「失败时邮件通知」 |
| Cloudflare Workers Cron | 每天 10 万次请求 | 写个 `scheduled` handler 发一次 `fetch` 即可 |

目标地址统一填 `https://你的面板地址/health`，返回 `{"status":"ok",...}` 且 HTTP 200 就算成功。三个渠道里建议至少配两个，`/health` 的请求量很小，不会触发限流。

### 还有更彻底的方案

如果平台允许挂载持久卷并固定实例数（通常是绑定支付方式后的付费规格），直接改成常驻实例，就不需要保活。保活只是免费额度下的权宜之计，它的可靠性受第三方定时器影响。

## 四之二、部署到免费 PaaS（可选）

免费额度也能跑，但有两个前提必须先搞明白，否则一定会出问题。这一节用「平台」泛指任何免费容器托管服务（能连 GitHub、按仓库里的 `Dockerfile` 构建、给一个带 SSL 的域名那种）。

### 两个必须先知道的特点

1. **闲置一段时间会休眠**。有请求进来就唤醒，冷启一般几秒。休眠期间调度器不跑，定时签到会漏 → 靠「外部定时唤醒」（第四节第二层）+「每日补签」（第五节第 5 步）解决。
2. **容器内文件每次重新部署都会清空，没有持久卷**。这是最关键的：SQLite 和登录会话都会没 → 靠「备份 + 启动时自动恢复」（第七节）解决。

### 部署步骤

1. 把仓库推到 GitHub（本仓库就是模板，可以直接 fork）。
2. 在平台控制台新建项目 → 连接 GitHub → 选仓库和分支。
3. 平台会自动识别仓库根目录的 `Dockerfile`。构建方式和本机 `docker build` 一样，不用额外配置。
4. 设置环境变量（`Environment`）：

   | 变量 | 建议值 | 为什么 |
   | --- | --- | --- |
   | `PANEL_PASSWORD` | 一个强密码 | 面板第一次初始化就用它 |
   | `TZ` | `Asia/Shanghai` | cron 按这个时区解释 |
   | `DATA_DIR` | `/app/data` | 保持默认即可 |
   | `PUBLIC_URL` | `https://平台分配给你的域名` | 让保活自检知道该请求谁 |
   | `TGCK_CONFIG` | 老实例导出的 JSON（可选） | 空库时自动导入，一次性迁移用 |

5. 点 Deploy，等构建完成，访问平台给的域名。

### 数据迁移过来

第一次部署完是空库。两种搬法：

**A. 手动（稳，推荐第一次用）**

1. 老实例面板 →「系统设置 → 备份与恢复」→「下载备份文件」，拿到 `tgck-xxxx.json`
2. 新实例登录 → 同一页 → 恢复方式选「替换」→「从文件恢复…」→ 选中那个文件 → 确认
3. 顺便在「WebDAV 云备份」或「GitHub 同步」里配好并打开自动备份，之后容器重建会自动恢复

**B. 环境变量（适合能改平台配置的情况）**

把老实例导出的 JSON 压成一行塞进 `TGCK_CONFIG`，新容器空库启动时会自动导入。但会话字符串很长，容易超出环境变量长度上限，通常还是走 A。

### 部署后要做的三件事

1. **配外部定时唤醒**：仓库自带的 `.github/workflows/keepalive.yml`，把 `PANEL_URL` 设成平台给你的域名。不配的话实例会睡，签到会漏。
2. **配云端备份**：WebDAV 或 GitHub 至少一个，打开自动上传，再打开「启动时自动恢复」。这是没有持久卷时唯一的数据保障。
3. **验证一次**：面板上点「立即备份一次」和「立即补签一次」，两个都成功就说明链路通了。

### 免费额度够不够

签到这种一天几次、每次几百毫秒的负载，免费规格（通常 0.25~1 vCPU、512 MB 内存、几百 MB 到 1 GB 磁盘）完全够。SQLite 只有几百 KB，备份文件每个约 10–20 KB（14 份也就 300 KB）。主要限制是休眠和重建，上面两个机制就是为它们准备的。

## 五、面板使用流程

面板有六个页签，第一次用建议按「账号 → 机器人 → 群组 → 设置」的顺序走一遍。

### 1. 加账号（只有「用自己的账号签到」才需要）

「账号与登录」页签 → 填备注名、手机号（带区号，如 `+8613800138000`）、API ID、API Hash → 「保存账号」。可以重复这一步加多个账号。

每个账号单独一行，有独立的登录状态和会话。加完点该行的「登录」选中它，然后：

- **扫码登录**（推荐）：点「扫码登录」，用手机 Telegram（设置 → 设备 → 连接设备）扫一下，不用等短信。
- **验证码登录**：点「用验证码登录」，验证码会发到该账号的 Telegram（一般在 Saved Messages 或官方通知里）。

开启了两步验证的账号会再要求输入验证密码。两种方式都会把会话存进各自账号记录，重启容器不用重新登录。

> 编辑账号时 API Hash 故意不回填，留空表示「不修改」。想换就填新的。

### 2. 加机器人（只有用机器人签到 / AI 聊天才需要）

「AI 机器人」页签 → 粘贴 BotFather 的 token → 「校验并添加」。可以加多个，各自独立轮询。

机器人必须已经被拉进目标群，并且能在群里发言。私聊使用则先在 Telegram 里给它发一句话。

同一页往下有「AI 智能体」，可以建多个，每个配自己的模型和人设：

| 字段 | 说明 |
| --- | --- |
| 名字 | 自己认得出就行，例如「闲聊小助手」「客服机器人」 |
| 模型名 | 如 `deepseek-chat`、`moonshot-v1-8k`、`Qwen/Qwen2.5-7B-Instruct` |
| 接口地址 | 填到 `/v1` 为止，例如 `https://api.deepseek.com/v1` |
| API Key | 编辑时留空表示不修改 |
| 人设 / 提示词 | 决定它说话的风格和边界 |
| 上下文条数 / 最大长度 / 温度 / 最短间隔 | 按需调，越界的值会自动夹到合法区间 |

第一个建好的智能体会自动成为「默认」，机器人不指定就用它。想让某个机器人换个模型说话，在机器人表单的「用哪个 AI 智能体」里单独选即可。旧版本里那份单套 AI 配置会在升级后自动变成第一个智能体，不用重填。

### 3. 加群组

「群组管理」页签 → 填写：

| 字段 | 说明 |
| --- | --- |
| 群组名称 | 方便自己识别 |
| 群组链接 / 用户名 / ID | `@群用户名`、`-1001234567890`，或 `https://t.me/c/1234567890/45` |
| 签到指令 | 默认 `签到`（就是往群里发这两个字），也可填 `/checkin` 等，必须和该群要求一致 |
| 签到方式 | 跟随全局 / 用我的账号 / 用机器人 |
| 用哪个账号 | 选了「用我的账号」才生效，留空走默认账号 |
| 用哪个机器人 | 选了「用机器人」才生效，留空走默认机器人 |
| 签到时间 | 5 段 cron，每行一个 |

群组列表里有一列「执行者」，会直接显示这个群用谁签到，例如「用账号（主号）」「用机器人（@xxx_bot）」「跟随全局（机器人）」。

**找群 ID 不用手抄**：机器人已经在的群会出现在表单上方的快捷按钮里，点一下自动填入。

### 4. 设置

「系统设置」页签：时区、重试次数、随机延迟、通知会话。首次使用建议先开「模拟运行」跑一遍，确认连接和群组都没问题再关掉。

**「谁来签到」决定默认执行者**。群组里没单独指定时就用它。

### 5. 每日补签

默认开启。判定条件很直接：群组已启用 + 今天有计划时间已过 + 今天还没有成功记录 → 补一次。

- **补签检查间隔**：默认 600 秒，范围 120–3600。
- **同群补签冷却**：默认 1800 秒，避免反复失败刷屏。
- 补签产生的日志，来源列显示「补签」，和定时的「定时」区分开。

免费 PaaS 会休眠，定时点经常不在线。这个机制保证每天至少成功一次。想手动验证，点「立即补签一次」。

### cron 格式

```
分 时 日 月 周
```

| 表达式 | 含义 |
| --- | --- |
| `0 8 * * *` | 每天 08:00 |
| `0 8,20 * * *` | 每天 08:00 和 20:00 |
| `*/30 * * * *` | 每 30 分钟 |
| `0 9 * * 1-5` | 工作日 09:00 |

时区在「系统设置」中修改，例如 `Asia/Shanghai`、`Asia/Tokyo`、`UTC`。修改后调度任务会自动重载。

## 六、AI 聊天机器人

这条链路**完全不需要 api_id / api_hash**，只需要 BotFather 的 token。它和签到是两套独立机制：

| | 签到（机器人模式，默认） | 签到（账号模式） | AI 机器人 |
| --- | --- | --- | --- |
| 需要的凭据 | 只要 `bot_token` | `api_id` + `api_hash` + 手机号登录 | 只要 `bot_token` |
| 连接方式 | Bot API | MTProto（Telethon） | Bot API（HTTP 长轮询） |
| 以谁的身份发消息 | 机器人账号 | 你本人 | 机器人账号（Business 下可代你回复） |
| 能否完成群签到 | 能（少数只认真人的群除外） | 能 | 能 |

### 1. 创建机器人

1. 在 Telegram 搜索 **@BotFather**，发送 `/newbot`。
2. 按提示设置显示名和用户名（用户名必须以 `bot` 结尾，且全平台唯一）。
3. BotFather 会返回一行 token，形如 `123456789:AAHxxxxxxxxxxxxxxxxxxxxxxxxxxx`。
4. 面板「AI 机器人」页签 → 粘贴 token → 点「校验并保存 Token」。
5. 把「启用」改成开启。

### 2. 让机器人能收到消息

- **私聊**：直接在 Telegram 里找到你的机器人，点 Start 并发一句话即可。
- **群组**：把机器人拉进群。默认情况下 Bot 在群里只能看到 @ 它和回复它的消息，这正好对应「被 @ 才回」的触发方式。如果希望机器人读到群里所有消息（比如「群内所有消息都回」模式），需要找 @BotFather 发送 `/setprivacy`，选择你的机器人并设为 **Disable**，然后把机器人移出群再重新加入——隐私设置只在入群时生效。

### 3. 配置 AI 模型

在「AI 模型设置」里填四项：

| 字段 | 说明 | 示例 |
| --- | --- | --- |
| 接口地址 | 兼容 OpenAI 的 base_url，填到 `/v1` 为止 | `https://api.deepseek.com/v1` |
| 模型名 | 服务商文档里的模型标识 | `deepseek-chat` |
| API Key | 服务商后台申请的密钥 | `sk-...` |
| 人设提示词 | 决定机器人说话风格 | 「你是群里的助手，回答简短口语化」 |

其他可调项：**上下文条数**（带多少轮历史，0 表示不带，默认 12）、**最大回复长度**、**温度**、**最短回复间隔**（同一会话的限流，默认 3 秒）。

填完点「测试 AI 连通性」，返回一句回复就说明链路通了。

常见服务商的 base_url 参考（以各家最新文档为准）：

- DeepSeek：`https://api.deepseek.com/v1`
- 硅基流动：`https://api.siliconflow.cn/v1`
- 月之暗面 Kimi：`https://api.moonshot.cn/v1`
- 通义千问：`https://dashscope.aliyuncs.com/compatible-mode/v1`
- 自建 one-api / new-api 中转：`https://你的域名/v1`

**如果报 `[Errno 104] Connection reset by peer` 或连接超时**，这不是 Key 或模型名的问题，而是这台服务器到接口的网络不通，最常见的原因是接口（或你用的中转）只对大陆网络开放。判断方法：在能正常上网的国内机器上 `curl` 同一个地址能通，部署在境外云主机上就不通。

三种解法，按推荐顺序：

1. **换全球可达的服务**：DeepSeek、硅基流动、OpenRouter 等国内外都能访问，直接换 base_url 即可。
2. **在「出网代理」里填一个境外可用的 HTTP 代理**：形如 `http://user:pass@host:port`。填了之后所有 AI 请求都走代理，可以继续用原来的中转。
3. 让中转提供方换成境外可接入的线路。

「出网代理」留空表示直连，不影响 Bot API 和签到。注意代理必须是境外能连上的；如果代理本身在大陆，问题依旧。

### 4. 触发方式

在「接入机器人」里选择：

- **私聊 + 群里被 @ 或回复时**（默认，推荐）：最不打扰人，也不会被群管理当成刷屏。
- **群内所有消息都回**：只在很小的群或测试时用，容易触发 Telegram 限流。
- **只回私聊**：相当于一个私人 AI 助手。

### 注意事项

- 机器人回复会计入 Telegram 的 Bot API 限流（单群每分钟约 20 条）。别把「最短回复间隔」调得太小，也别选「群内所有消息都回」跑大群。
- 对话上下文存在 SQLite 的 `ai_messages` 表里，每个会话只保留最近 60 条。面板可以查看和清空。
- `bot_token` 和 `ai_api_key` 等同于密码，不要写进代码或公开仓库。

## 七、数据、备份与迁移

### 数据放在哪

所有数据都在 `DATA_DIR` 下的 `checkin.db`（默认 `/app/data/checkin.db`）：配置、Telegram 会话字符串、账号、机器人、群组和日志。Docker 部署时映射到宿主机的 `./data/`。

这个文件包含 Telegram 会话，等同于账号登录凭证，**不要泄露或上传到公开仓库**。

### 三种备份方式

| 方式 | 怎么用 | 适合 |
| --- | --- | --- |
| 下载备份文件 | 面板「系统设置 → 备份与恢复」→「下载备份文件」 | 一次性存档、换机器前手动带走 |
| WebDAV 自动备份 | 填 WebDAV 地址和账号，打开「自动上传」 | 坚果云、群晖、Nextcloud 用户 |
| GitHub 同步 | 填 Token 和仓库，打开「自动同步」 | 已经有仓库，顺便要版本历史 |

备份是一个 JSON：`app` / `format` / `version` / `created_at` / `settings` / `groups` / `accounts` / `bots` / `logs`。文件名形如 `tgck-20261125-034512.json`。

本地备份默认存在 `DATA_DIR/backups/`，保留份数可调（1–200，默认 14）。

### 自动备份

打开「自动备份」后，后台线程启动等 90 秒，之后每 N 小时（1–168，默认 12）跑一次：

- 本地**一定**存一份
- WebDAV / GitHub 各自看自己的「自动上传 / 自动同步」开关，开了才上传
- 各自按自己的保留份数裁剪旧文件

面板顶部会显示上次运行时间、上次目标、上次错误。

### 恢复

两种模式：

| 模式 | 行为 |
| --- | --- |
| 替换（replace） | 先清空当前的群组、账号、机器人，再导入备份里的 |
| 合并（merge） | 只补缺，按 `手机号+api_id`、`token`、群组标识去重，已存在的不动 |

恢复时账号和机器人的自增 ID 会变，程序会把群组里引用的 `account_id` / `bot_id` 改写成新的，不会指错人。

「面板密码」那一项选「保留当前密码」就不会被备份里的密码覆盖。

### 迁移到新平台

无持久卷的平台（容器每次重新部署都会清空）必须靠这个流程：

1. 老实例：面板 →「系统设置 → 备份与恢复」→「下载备份文件」，保存 `tgck-xxxx.json`
2. 新实例部署起来，用面板密码登录
3. 新实例：同一页 → 恢复方式选「替换」→「从文件恢复…」→ 选中刚才那个 JSON → 确认

数据、账号会话、机器人 token、AI 设置、面板密码全都会跟着过来。

**更省事的做法**：迁移前在老实例配好 WebDAV 或 GitHub 并上传一次，新实例部署后填好同样的地址（如果平台允许设环境变量，可以直接把配置塞进 `TGCK_CONFIG`），打开「启动时自动恢复」，下次容器重建就会自动拉回来。

### 全自动恢复（关键）

「启动时自动恢复」默认开启。逻辑是：启动时如果本地库为空（没有群组也没有账号和机器人），且 WebDAV 或 GitHub 已配置并开启自动上传，就从云端最新一份备份做一次 `replace` 恢复，**包括面板密码**。

这正好补上免费平台的短板：平台把容器重建后，数据自己就回来了，不用人工干预。

### 用 docker 命令行备份

不想用面板也可以直接复制数据库文件：

```bash
docker compose stop
cp data/checkin.db data/checkin.db.bak
docker compose start
```

或者只导出一份可迁移的 JSON：

```bash
docker exec tg-checkin python -c "from app import backup; print(backup.save_local())"
docker cp tg-checkin:/app/data/backups/. ./backups/
```

### WebDAV 怎么填

以坚果云为例：地址填 WebDAV 入口 `https://dav.jianguoyun.com/dav/`，用户名是登录邮箱，密码用「应用密码」（在账户信息 → 安全选项里生成，不是登录密码）。

「备份文件夹」是可选的一栏：留空就直接放上面那个地址里；填 `tg-checkin` 就在地址下建一个同名文件夹、备份全放里面，填 `backup/tgck` 这种多级路径也支持。**点保存时会自动在云端把文件夹建好**（缺失的每一级都会补），不用先去网页端手动新建。

群晖、Nextcloud 都类似，地址填到目录为止。填完点「保存设置」或「测试连接」，能看到「连接成功，已自动创建文件夹：…」就算通了。

### GitHub 怎么填

1. 建一个**私有**仓库专门放备份（公开仓库等于把会话泄露出去）
2. 生成 Personal Access Token：面板「GitHub 同步」里点 **「点这里一键生成」**，名称、有效期、`Contents: Read and write` 都已经预填好了，打开后只需在 `Repository access` 选 **Only select repositories** 勾上备份仓库，再点 Generate token
3. 面板填：Token、仓库 `owner/repo`、分支 `main`、目录 `tgck-backups`（仓库这一栏也可以直接粘 `https://github.com/owner/repo`，会自动截成 `owner/repo`）
4. 点「测试连接」，显示「私有仓库」就对了

> 想手动创建也可以：`Settings → Developer settings → Personal access tokens → Fine-grained tokens`，权限只勾该仓库的 `Contents: Read and write`。一键链接用的是同一套官方 URL 参数，只是把字段填好了。

每次备份会作为一次 commit，历史里能回滚到任意一份。

> 报「GitHub 不认这个 Token」= token 过期或被撤销；报「没有 repo 权限」= token 权限不够。报「找不到仓库」时，程序会用你的 Token 反查它**实际能访问哪些仓库**，直接告诉你仓库名该怎么写、或者是不是 `Repository access` 没勾上——GitHub 对「仓库不存在」和「没权限」回的是同一个 404，光看状态码分不出来。

## 八、常见问题

**1. 申请不到 api_id / api_hash**

见第一节末尾的「申请不到 api_id 怎么办」。核心是：换一个 Telegram 账号去申请（凭据是应用凭据，与登录账号无关），或者先确认自己是不是已经申请过。如果只是想要群里的 AI 聊天机器人，那个模块完全不需要 api_id。

**1.5 机器人签到报「找不到这个群」/「机器人不在群里」**

说明机器人还没进群，或群 ID 填错了。做法：把机器人拉进目标群 → 在群里发一条消息 → 面板填 `-100` 开头的完整群 ID（或 `@群用户名`）。如果机器人已被踢出，重新拉进去即可。报「没有发言权限」则是群内限制，需要解除限制或给机器人管理员权限。

**1.6 报 `ChatAdminRequiredError: Chat admin privileges are required…`**

说明你填的目标是「频道」而不是群：在频道里发言必须是管理员，普通账号和机器人都发不进去，Telegram 直接回这个错。现在程序会先用 `getChat` / `get_entity` 看一眼，如果是频道就自动改发到它的关联讨论群，并在日志备注里写明；如果频道没有开讨论群，请改成 `-100` 开头的群 ID 或群链接 `https://t.me/c/<数字>/1`。另外，脚本也会在账号方式失败时自动改用机器人补发一次，日志会写清是哪一边失败、哪一边成功。

**2. 机器人不回消息**

按顺序排查：面板里「启用」是否为开启 → token 是否校验通过 → 私聊里是否先给机器人发过 Start → 群聊里是否 @ 了它（或回复了它的消息）→ 如果选了「群内所有消息都回」但仍收不到，说明 Bot 的隐私模式没关（见第六节第 2 步）。「机器人状态」一栏会显示最近错误。

**3. AI 报 401 / 404**

401 是 API Key 错误，404 一般是 base_url 或模型名写错。base_url 要填到 `/v1` 为止，不要带 `/chat/completions`。

**3.1 AI 报 `[Errno 104] Connection reset by peer` / 连接超时**

不是 Key 的问题，是这台服务器到接口的网络不通。详见第六节第 3 步的说明，通常是接口只对大陆网络开放，换全球可达的服务或填「出网代理」即可。

**4. 签到日志里有机器人回复，但提示失败**

说明命中了「失败关键词」（在系统设置里配置）。有些群的签到机器人会回复「今日已签到」「重复签到」，按你的需要决定哪些算失败。

**5. 改了 cron 不生效**

保存后会自动重载调度，当前任务数可在概览页看到。如果 cron 表达式非法，保存时就会返回 400。

**6. 收不到 Telegram 验证码**

确认手机号带区号；确认 API ID/Hash 正确；网络受限时配置代理。验证码有时会被 Telegram 归到「Saved Messages」。

**7. 提示触发限流（FloodWait）**

Telegram 要求等待若干秒，按提示时间过后再试，不要连续重试。

**8. 提示无法访问群组**

你的 Telegram 账号必须先加入该群；私有群建议用邀请链接或 `https://t.me/c/群ID/任意消息ID`（程序会自动转成 `-100群ID`）。

**9. 消息发出但机器人不回复**

检查签到指令是否正确，有些群要求不带 `/`，有些要求纯文本（例如 `签到`）。可在「系统设置」里填失败关键词辅助判断。

**10. 面板打不开**

确认 `docker compose ps` 中容器 healthy，确认服务器安全组放行了 8000 端口。

**11. 忘记面板密码**

密码保存在数据库中，`.env` 里的 `PANEL_PASSWORD` 只在首次初始化时生效。可在宿主机执行下面的命令重置为 `admin123`（不会丢失其他配置）：
```bash
docker exec -it tg-checkin python -c "from app import db; db.init_db(); db.set_setting('panel_password','admin123')"
docker compose restart
```

**12. 备份文件里到底有什么？恢复会覆盖现有配置吗**

备份是一个 JSON 文件，包含面板设置、群组、账号（含登录会话）、机器人、日志，但不含任何图片文件。恢复时有两种模式，界面上必须选一个：

- `replace`（覆盖）：先清空现有群组、账号、机器人，再写入备份内容。适合「换机器」「推倒重来」。
- `merge`（合并）：按手机号+api_id、机器人 token、群组 chat 去重，只补不删。适合「把另一台机器的配置并过来」。

`replace` 不会删除数据库里剩余的旧日志（日志是追加的），但账号、机器人、群组会被严格对齐到备份里的状态。恢复会自动重载调度，不需要重启。

**13. WebDAV 测试连接失败**

按报错对应处理：`401` 是用户名或应用密码不对（坚果云要用「应用密码」，不是登录密码）；`403` 是这个账号对目标目录没有写权限；`404` 是地址层级不对，注意「WebDAV 地址」填到目录为止，要新建的子文件夹写在「备份文件夹」那一栏（保存时会自动逐级 `MKCOL` 建出来）；`405` 说明填的是网页首页而不是 WebDAV 入口，坚果云是 `https://dav.jianguoyun.com/dav/`。

**14. GitHub 同步报错**

`401` 是 Token 失效或被撤销，重新生成；`403` 是 Token 没有 `Contents: Read and write` 权限，或触发了速率限制；`404` 表示 GitHub 找不到这个仓库——它把「仓库不存在」和「Token 没被授权访问」都算成 404，所以程序会在报错里列出这个 Token 实际能访问的仓库，照它说的改就行。私有仓库必须在 Token 的 `Repository access` 里显式勾上。仓库名写 `owner/repo` 即可，粘带 `https://github.com/` 的完整链接也能自动识别。

**15. 在免费 PaaS 上重启后数据全没了**

这是平台特性：免费容器**没有持久卷**，每次重新部署（或平台重建容器）都会把容器内的文件清空。所以必须做下面两件事之一：

- 在「系统设置 → 备份与恢复」里打开「启动时自动恢复」，并把 WebDAV 或 GitHub 的「自动同步」也打开。程序启动时发现数据是空的，会自动从云端拉最新一份备份恢复（包括面板密码）。
- 或者手动：部署前在老实例点「下载备份文件」，部署后在新实例点「从文件恢复…」。

**16. 每日补签没生效**

补签依赖「签到状态表」判断今天有没有成功过，第一次运行时表是空的，会按正常定时任务走。运行逻辑是：调度每分钟检查一次，发现有群组今天还没签到成功、且当前时间已过它的 cron 时间，就补一次；同一个群两次补签之间至少隔 30 分钟（冷却），两次检查至少隔 10 分钟。所以「上线后过几分钟才补」是正常现象，日志来源会标成「补签」。如果一直不补，先确认定时任务本身是启用状态、账号在线。

**17. 备份文件能不能传到网盘以外的地方**

可以，备份就是普通 JSON，随便存。只是想提醒一句：**文件里有账号登录会话（session）和面板密码**，等同于把账号交给了拿到文件的人，别往公开仓库或公共网盘扔。
